## 제품 목표

서울에서 데이트할 장소를 고르는 사람이 **지역·분위기·상황 중 원하는 조건으로 바로 탐색을 시작하고, 여러 조건을 조합해 후보를 좁힐 수 있게 한다.** 예를 들어 서촌으로 먼저 좁힌 뒤 조용한 실내 카페를 찾거나, 비 오는 날에 갈 만한 곳을 먼저 고른 뒤 방문하기 가까운 지역을 선택할 수 있다.

첫 출시는 서울 **5~7개 탐색 지역**을 대상으로 한다. 6곳 예시로 서촌·북촌·익선동·성수·연남·망원을 제안한다. 지역은 행정구역보다 방문자가 장소를 찾을 때 쓰는 이름으로 관리하고, 새 지역은 데이터 추가로 노출한다. 코스 만들기는 장소 탐색 흐름을 검증한 뒤 확장한다.

## 첫 버전 범위

| ID | 기능 | 화면 동작과 완료 기준 |
| --- | --- | --- |
| FR-01 | 장소 탐색 | `/places`에서 지역·분위기·상황을 동등한 탐색 진입점으로 제공한다. 카드에 장소명, 지역, 카테고리, 주요 태그, 대표 사진 또는 기본 이미지를 표시한다. 한 번에 12개씩 조회하고 더 보기를 제공한다. |
| FR-02 | 장소명·지역 검색 | 장소명과 지역 이름을 검색한다. 검색어와 필터를 함께 적용하며 URL로 조건을 공유할 수 있다. 새 검색 조건에는 1페이지부터 요청하고, 이전 조건의 늦은 응답으로 목록이 덮이지 않는다. |
| FR-03 | 장소 필터 | 지역·분위기·상황·실내외·카테고리로 좁힌다. 같은 필터 종류의 여러 값은 그중 하나에 해당하면 통과하고, 다른 종류의 조건은 모두 만족해야 한다. 목록은 최근 등록순으로 표시한다. |
| FR-04 | 장소 상세·지도 링크 | `/places/:id`에서 주소, TourAPI 소개, 큐레이션 한줄 소개, 태그, 사진 및 정보 확인일을 확인한다. 카카오맵에서 위치를 보거나, 검증한 네이버지도·카카오맵 링크를 연다. 소개·태그·사진이 없으면 해당 영역을 생략하거나 기본 이미지를 표시한다. 운영 상태는 방문 전 외부 지도에서 다시 확인할 수 있게 안내한다. |
| FR-05 | 주변 장소 실시간 검색 | 상세 화면에서 ‘주변 장소 찾기’를 누르면 카카오 로컬 API로 검색한다. 현재 열어 본 상세 장소의 좌표를 기준으로 1km 안의 카페 또는 음식점을 거리순으로 찾는다. 브라우저 위치 권한은 요청하지 않는다. 결과는 외부 카카오맵 링크로 연결하고, 자체 상세·최근 조회 대상은 자체 등록 장소로 한정한다. |
| FR-07 | 최근 조회 | 상세 조회가 성공한 장소를 동일 브라우저에 최대 20개까지 보관한다. 같은 장소를 다시 보면 맨 위로 이동한다. `/recent`에서 다시 열거나 기록을 지울 수 있다. 목록 클릭이나 프리페치만으로는 기록하지 않는다. |

예시 필터는 분위기 ‘조용한·아늑한·트렌디한’, 상황 ‘비 오는 날·퇴근 후’, 카테고리 ‘카페·식당·전시·산책’이다. ‘퇴근 후’는 편집자가 붙이는 추천 태그로 운영하고, 오늘 영업 중임을 보장하는 표시와 구분한다.

외부 지도 링크는 지도 앱이나 웹으로 이동하는 버튼이다. 앱 안에서 지도를 띄우고 핀을 움직이며 탐색하는 기능에는 지도 SDK와 별도 화면이 필요하므로 후속 후보로 둔다. 코스 만들기와 저장도 후속 범위다. 첫 버전에 기능을 더할 때는 아래 착수 순서와 세 문서를 함께 갱신한다.

## 데이터와 사진 운영

| 데이터 | 초기 운영 방식 |
| --- | --- |
| 메인 장소 목록과 상세 | 한국관광공사 TourAPI에서 지역과 유형으로 후보를 수집하고, 이용 가능한 기본정보를 PostgreSQL에 저장한다. 메인 목록과 상세는 Express가 DB에서 제공한다. 초기 공개 작업 목표는 30~50곳이며 후보 지역별 표본을 확인해 조정한다. |
| 소개와 태그 | TourAPI가 제공한 소개와 운영자가 추가한 한줄 소개를 구분한다. 분위기·상황·실내외 분류는 근거를 확인한 경우에 추가한다. 확인 전에는 미분류로 두고 해당 필터 결과에서 제외한다. |
| 주변 데이터 | 카카오 로컬은 상세 장소 좌표를 기준으로 주변 카페·음식점을 실시간 검색한다. 응답은 검색 화면에 표시하며 메인 목록 DB에 넣지 않는다. |
| 사진 | TourAPI 사진은 이미지별 이용 근거와 출처 표시 문구를 확인한다. 초기에는 공공누리 1유형으로 확인된 사진을 우선 사용하고 노출하는 곳에 출처를 표시한다. 변경금지 조건이 있거나 이용조건을 확인하지 못한 사진은 첫 버전에서 기본 이미지로 대체한다. |
| 정보 갱신 | 가져오기 작업을 다시 실행해 같은 TourAPI 장소 ID의 기본정보를 갱신한다. 운영자 분류는 보존한다. 동기화 시각과 현장·운영 정보 확인일을 구분하며, 공개 중단이 확인된 장소는 숨긴다. |

**확정된 범위**는 관광지·문화시설 중심이다. TourAPI에서 확보 가능한 음식점·카페도 포함한다. 서울시 문화행사는 장소 탐색 출시 후 별도 기능으로 추가한다.

**장소는 자동 검사를 통과하면 공개한다.** TourAPI에서 수집한 신규 후보의 이름·주소·좌표·카테고리를 확인하고, 서비스의 탐색 지역에 명확히 배정되며 중복이 의심되지 않으면 목록과 상세에 표시한다. 필수값이 누락되거나 지역 배정이 애매하거나 중복이 의심되면 공개를 보류하고 해당 후보만 검토한다. 사진 사용 조건이 불명확하면 기본 이미지를 표시하고, 확인되지 않은 분위기·상황 태그는 비워 둔다.

## 화면 상태와 검증

- 목록은 최초 로딩, 결과 없음, 서버 오류를 구분한다. 더 보기 실패 시 기존 카드를 남기고 해당 페이지를 다시 요청한다.
- 상세의 주변 검색 실패, 한도 초과, 결과 없음은 주변 검색 영역에서 안내한다. 기본 상세와 지도 링크는 계속 쓸 수 있다.
- 삭제 또는 비공개 장소는 상세에서 이용할 수 없다고 안내하고 최근 조회 화면에서 기록을 지울 수 있게 한다.

## 기술과 구현 범위

재성님이 JavaScript·React 클라이언트를 직접 구현하고, CSS는 요청한 부분을 지원한다. 서버와 DB는 Express·PostgreSQL·Prisma로 설계한다. 로컬 PostgreSQL은 Docker 사용을 우선 검토하고 서버 의존성과 분리한다. API와 DB 설계, 시드, 마이그레이션, 서버 구현과 검증은 지원을 받을 범위다.

구현 순서는 기간을 고정하지 않고 단계별로 관리한다. 주 5일·하루 4~5시간은 가용 시간의 참고치다.

1. TourAPI 후보 표본 확인, DB 설계와 가져오기 작업, 지역·태그 목록, 장소 목록 및 상세 API
2. React 탐색 화면, 검색·필터, 상세와 지도 링크
3. 최근 조회, 주변 검색과 실패 상태
4. 출시 데이터 검토, 모바일 동작 검증, 성능 측정 및 개선 기록

| TourAPI 일시 중단 | 정상 동기화 직후와 외부 API 장애 동안 목록·상세 조회 | 조회 성공 여부, 사용자 요청 경로의 TourAPI 호출 건수, 마지막 성공 동기화 시각 |
| 목록 조회 성능 | 공개용 시드와 별도로 만든 테스트 시드에서 조회 실행 계획 비교 | 데이터 수, API 응답 시간, DB 쿼리 시간, `EXPLAIN ANALYZE` 결과 |

동일한 데이터·브라우저·네트워크 조건으로 변경 전후를 각각 5회 이상 측정해 중앙값과 재현 절차를 남긴다. 공개용 데이터와 성능용 합성 데이터를 구분한다. PR에는 문제 상황 → 선택한 해결책과 이유 → 감수한 비용 → 측정 결과 순서로 기록한다.

## 검토할 결정

| 항목 | 초안의 기본값 | 확정 시 영향 |
| --- | --- | --- |
| 초기 대상 지역·장소 | 6개 후보 지역, 30~50곳 목표 | 실제 수집 가능 여부를 보고 목록을 확정한다. |
| 지역별 데이터 충실도 | TourAPI 후보 표본 | 사진 보유율과 이용조건 확인 가능 비율, 주소·좌표·소개 누락률, 지역·카테고리별 후보 수를 확인한다. |

장소 수집은 [한국관광공사 국문 관광정보 서비스](https://www.data.go.kr/data/15101578/openapi.do)를 참고한다. 주변 검색 연동 기준은 [카카오맵 REST API 문서](https://developers.kakao.com/docs/ko/kakaomap/rest-api)와 [쿼터 안내](https://developers.kakao.com/docs/ko/getting-started/quota)를 참고한다.
